# 一致性測試套件（第 1 層編碼、第 2 層行為、第 3 層時間、第 4 層錯誤偵測）

**要回答的問題**

- 第 1 層：我們的工具產生的位元組，硬體解出來是不是同一道指令？
- 第 2 層：同一支程式，硬體做的事、做的順序，和模擬器一樣嗎？
- 第 3 層：每道指令花的週期數，硬體和模型一樣嗎？（量測用，見下方「第 3 層」）
- 第 4 層：遇到不該執行的指令，硬體怎麼反應？（見下方「第 4 層」）

做法：十五支很短的程式（第 1 層十支、第 2 層五支），每支針對一件事，把結果寫到「結果 CSR」。在 RTL 模擬（或 FPGA）跑同一份映像，把 CSR 被寫入的值和預期表比對。
值不同的那一格會指出是哪個編碼假設錯了。背景見 `docs/SIM_VS_SPEC.md` 第 4 節與 `docs/PROJECT_STATUS.md` 7.4（D1–D6）。

**不需要等任何問題的答覆就可以開始**：這套測試本身就是在回答那些問題。

## 第 2 層：五支行為測試

第 2 層除了最後的值，還要看**順序**：哪個位址先被寫入、I2C 匯流排上依序出現哪些交易。只比順序，不比時間。

| 測試 | 檢查什麼 | 需要板子的 CSR | 對應的問題 |
|---|---|---|---|
| `b01_timers` | **Main 與 Peri 的計時器是兩顆還是一顆** | 是 | `docs/SIM_VS_SPEC.md` 的 **Q1** |
| `b02_poll_ready` | Poll 單元：遮罩、arm、讀到 ready 才往下 | 是 | — |
| `b03_slot_overrun` | 結果槽：連續發佈兩次時保留第一筆、設 overrun | 否 | — |
| `b04_nack_error` | 沒有裝置回應時設 error 旗標、旗標保持、程式繼續 | 否 | — |
| `b05_done_error` | Main 看到的 `PERI_NO_ERROR`／`PERI_ERROR`；service reset | 是 | — |

**`b01` 怎麼分辨一顆或兩顆**：Peri 先啟動一個很長的計時；Main 接著啟動自己很短的計時，而且做兩次。
兩顆獨立時，Peri 的標記（`RES+8`）一定在 Main 兩次短計時（`RES+0`、`RES+1`）之後才出現。
如果硬體只有一顆，Main 啟動計時器時會把 Peri 正在等的那一次蓋掉，Peri 的標記就會提前出現在 `RES+1` 之前。
這個判斷只看順序，不需要量時間。我們用環境檔模擬過「一顆共用的計時器」，`b01` 確實會因此失敗。
本專案已把計時器**定義為兩顆獨立的**（`docs/TIMERS.md`）；`b01` 就是驗證硬體符合這個定義的方法，完整的判定準則（V-1～V-4）與判讀表在該文件第 3 節。

**需要板子 CSR 的三支**（`b01`、`b02`、`b05`）會寫計時器週期、啟動位元、poll 遮罩與控制、done／error 位元。
規格只給了這些暫存器的名稱，沒有位址與位元；`conf_board.inc` 裡目前是範例值。**上硬體之前請先改成實際的數值，再重新執行產生器。**
如果板子上某個功能的做法不同（例如計時器週期不是兩個位元組），那一支測試的程式也要跟著改——請告訴我們實際的介面。

**測試平台需要的 I2C 裝置**（各支在 `EXPECTED.md` 有詳列）：`0x2B`（`b02`、`b05`）、`0x2C`（`b03`）；位址 `0x2D` **不可以**有裝置（`b04`、`b05`）。

## 第 3 層：八支量測程式

**這一層沒有「正確答案」。** 模型裡每道指令的週期數是等 RTL 提供的規劃值，所以第 3 層不是「對或錯」的測試，而是**量測工具**：
在硬體上量出數字，回填進模型，讓模擬器的時間和硬體一致。

| 程式 | 量什麼 | 需要 |
|---|---|---|
| `t01_alu` | ALU 一般運算、MUL | |
| `t02_mov` | MOV 1 個與 8 個位元組（分出固定部分與每位元組部分） | |
| `t03_branch` | 分支：不成立、成立 | |
| `t04_csr` | EXEC_CSR：WRITE8、SET8、READ8、WRITE_SP 1 個與 8 個位元組 | 結果 CSR 可讀回 |
| `t05_peri` | Peri 的 EXEC_CSR、分支、EXEC_PUB 1 個與 8 個位元組 | |
| `t06_xfer` | EXEC_XFER：讀 1 個、讀 4 個、寫 1 個位元組的 I2C 交易時間 | I2C 裝置 `0x2E`（任何暫存器都回 ACK） |
| `t07_timers` | Main 與 Peri 計時器每個 tick 是幾個 ISA 週期 | 板子的 CSR（`conf_board.inc`） |
| `t08_csr_contended` | Peri 不停寫 CSR 時，Main 的 EXEC_CSR 變慢多少（等仲裁器） | 與 `t04` 的 WRITE8 比較 |

**量法**：每個項目是三個標記（對 `RES + k` 的 CSR 寫入）之間的兩段，分別夾著 N1 與 N2 道同樣的指令：

```
一道指令的時間 = （第二段的週期數 − 第一段的週期數） ÷ （N2 − N1）
```

兩段相減會消掉標記自己的時間，所以只要量「兩次 CSR 寫入之間隔了幾個 ISA 週期」，不必知道寫入出現在指令的哪個時刻。

**步驟**

1. `python3 conformance/make_timing.py --bin-dir <工具資料夾>`：產生程式、映像（`out/tNN_*/`）與 `TIMING.md`。
2. 在硬體上執行各支程式，量出 `timing_measured_template.csv` 裡每一列兩個標記之間的 ISA 週期數，填在 `cycles` 欄（量不到的列留空）。
3. `python3 conformance/make_timing.py --bin-dir <工具資料夾> --measured 您的檔.csv`：
   報告會把量到的「一道指令的時間」和模型在三種取指方式下的預測並排，指出最接近哪一種，並算出「如果是那種取指方式，執行週期應該是多少、要改哪個參數」。
4. 把得到的數值寫進專案的 `.simparams`，並標記 `KEY.status = measured`。之後可以用 `--params 您的.simparams` 重新產生預測，再比一次，直到一致。

一道指令的時間＝取指＋執行。取指那一部分取決於硬體怎麼取指（EEPROM 或 SRAM，見 `docs/SIM_VS_SPEC.md` 1.2），差距達上千倍，
所以**第 3 層的第一個收穫就是看出硬體是哪一種取指方式**：`t01` 的 ALU 量出來是幾個週期還是幾千個週期，一看便知。

**這個工具本身驗證過什麼**：關掉取指時間時，十八個項目的「一道指令的時間」都等於規格 14.3／14.4 的規劃公式（由產生器獨立計算，例如 I2C 讀 1 個位元組 2432、讀 4 個 4255、寫 1 個 1825）；
計時器的 tick 是 2 個週期；有競爭的 CSR 寫入不會比沒有競爭的快。我們也拿「另一組參數的模型」當成假想的硬體去量，比對工具正確指出了取指方式與每個被改動的參數。

**限制**：量測的精度取決於能否以 ISA 週期為單位觀察 CSR 寫入的時刻；`t07` 的每段等待會多出最多一圈輪詢迴圈的時間（相減後誤差很小）；
`t08` 的結果與兩邊的相對時序有關，只適合拿來看「有沒有變慢、大約多少」；影像時序、事件派送、結果槽取用的延遲還沒有量測程式。

## 第 4 層：四十八份故意寫壞的映像

**要回答的問題**：`docs/HW_FAULT_DETECTION.md` 那張表的每一列——指令的位元組不合法、或違反規格的規則時，硬體在哪一級發現、之後怎麼反應？
那張表原本只能請人憑設計填寫；這一層讓每一列都有一份可以實際執行的映像。

**做法**：組譯器不會產生不合法的指令，所以每份映像分兩步做——先組譯一支合法的小程式（載體），再改掉映像裡的一兩個位元組，
讓其中一道指令變成那一列所說的情形。載體用標記把那道指令夾住：`RES+0 = 0xF0`（下一道就是受測指令）、`RES+1 = 0x0F`（之後的程式繼續執行了）、`RES_DONE`（跑到結尾）。

- **模型的行為**：在受測指令處報錯並停止，所以 `RES+0` 有、`RES+1` 與 `RES_DONE` 沒有。
- **硬體上要看的**：這三次寫入各有沒有出現；有沒有回報錯誤、在哪一級；之後 sequencer 是停住、繼續還是重置。
- **模型不是標準答案。** 硬體若不偵測某一項（照樣往下執行），請照實記錄，模擬器會跟著改——這正是那張表要收集的資訊。

涵蓋 55 列中的 48 列（編號與表格相同：共通 F、Main 的 M／B／V／L、事件 E、Peri 的 P／R／U／X）。沒有納入的 7 列與原因列在 `FAULTS.md` 最後，
主要是需要改 layout 暫存器、需要事件來源、或取決於板子的選項。

**步驟**

1. `python3 conformance/make_faults.py --bin-dir <工具資料夾>`：產生載體、改過的映像（`out/f_<編號>/`）與 `FAULTS.md`。
2. 每個案例載入 `out/f_<編號>/f_<編號>.*`（改過的邏輯映像、EEPROM 映像或 SRAM 字，三種內容一致；layout 檔沒有改）。
   `f_<編號>_carrier.*` 是未改動的載體，它的 `.lst` 可以看出受測指令原本是什麼；載體本身會正常跑到結尾，可以先用它確認測試平台沒問題。
3. 記錄三個標記與硬體的反應，填進 `faults_result_template.csv` 或 `docs/HW_FAULT_DETECTION.md` 的「硬體偵測級別」欄。

Peri 的案例（P、R、U、X）需要測試平台在位址 `0x2F` 有一個會回 ACK 的 I2C 裝置。

**這個工具本身驗證過什麼**：每支載體在模擬器上都正常跑到結尾（所以錯誤只來自那一兩個位元組的改動）；每份改過的映像都在受測指令處報出表格所列的錯誤碼；
三種格式（邏輯映像、EEPROM、SRAM 字）的內容逐位元組一致。

**特別留意 B6**（分支目標落在指令中間）：模型**不檢查**這個條件，它報的錯只是把立即值當成指令去解的結果。這一列最需要硬體的實際答案。

## 怎麼用

### 1. 產生映像檔

```
python3 conformance/make_conformance.py --bin-dir <asmc 與 asmsim 所在的資料夾>
```

Windows 上例如 `--bin-dir D:\swork\AssemblyCore\dist\msvc2026`。產生器會組譯全部程式、用本專案的模擬器跑一遍確認與預期相同（第 2 層在「取指不花時間」與「每道指令讀 EEPROM」兩種模式下各跑一次），
再確認「解碼端用錯的編碼、或只有一顆共用計時器時，測試抓得到」，最後把檔案放進 `out/`。

結果 CSR 的預設基底是 `0x600`（占 `0x600`–`0x67F`）。如果這段位址在您的板子上是有作用的暫存器，換一段：`--res-base 0x700`。

### 2. 把映像載入 RTL

每支測試在 `out/cNN_*/` 下有同一份程式的幾種格式，挑 RTL 測試平台用的那一種：

| 檔案 | 格式 | 適用 |
|---|---|---|
| `*.main.bin`、`*.peri.bin` | 邏輯映像的原始位元組（程式碼、描述子表、常數池／DeviceMap） | 自己有載入器 |
| `*.main.hex`、`*.peri.hex` | 同上，Intel HEX | |
| `*.main.layout.json`、`*.peri.layout.json` | 六個區段的起始位置。**映像本身不含這些位置，硬體需要它們才找得到表** | 一定要一起用 |
| `*.sram.hex` | 共用程式 SRAM 的 32 位元字（兩份映像已依 base word 擺好） | 直接初始化 SRAM（規格 v31 的做法） |
| `*.boot.json` | 開機載入計畫：每個字寫到哪、layout 暫存器的值 | Boot 模組的測試平台 |
| `*.eeprom.bin`、`*.eeprom.hex`、`*.eeprom.json` | I2C EEPROM 的內容與各區域的位址 | 從 EEPROM 取指的硬體 |
| `*.lst` | 清單：每道指令的位址、位元組、解讀後的描述子 | 對照「這個位元組我們認為是什麼」 |
| `*.expected.csv` | 預期值 | |

第 1 層只有 `c10` 有 Peri 映像；第 2 層除了 `b04`（只有 Peri）之外都是 Main 與 Peri 兩份。

### 3. 執行並比對

- 讓程式跑到 `RES_DONE`（預設 `0x67F`）被寫入 `0xA5` 為止。
- 記錄執行期間所有 CSR 寫入（位址、值）。**看的是匯流排上的寫入，不必真的有那些暫存器**——只有標了「取決於：結果 CSR 必須是寫什麼讀回什麼的一般暫存器」的幾列（`c01` 的 SET8／CLR8、`c09`）需要那段位址能讀回寫入的值。
- 對照 `EXPECTED.md`：每個位址**最後一次**被寫入的值應等於預期值；標「不可被寫入」的位址不應出現任何寫入。
- `c10` 另外要在測試平台放一個 I2C 裝置（位址、暫存器內容寫在 `EXPECTED.md` 該節），並核對匯流排上的三筆交易。
- 第 2 層：另外核對 `EXPECTED.md` 各節的「寫入的先後順序」（以每個位址**第一次**被寫入的時刻比較）與「I2C 匯流排上應該看到的交易」。`b04` 的完成標記由 Peri 寫入。

### 4. 結果不同時

每支測試在 `EXPECTED.md` 都有「結果不同時怎麼判讀」。運算元是特意挑的，讓每種運算的結果都不一樣，所以從錯的值就能反推硬體實際用的編碼。
例如 `c03` 的 SUB 那一格出現 21（MUL 的結果），就知道硬體把我們的 SUB 編碼當成 MUL。

把結果告訴我們之後：ALU 的編碼、位元組序、DeviceMap 排列都是 profile 的鍵，改設定檔即可；只有移位方向要改一行程式。

## 預期值是怎麼來的

預期值是產生器**依規格 v31 的文字重新算的**（`make_conformance.py` 裡的 `alu_out`、`shift_out`、`cmp_true`），沒有呼叫模擬器。
之後才用模擬器跑同一批程式，兩邊必須一致（第 1 層 160 個數值全部一致）。第 2 層的預期行為則是依規格的敘述逐支寫定的。所以它同時是工具自己的回歸測試（`ctest` 的 `conformance_kit`）。

有幾個預期值建立在規格沒有明寫的地方，`EXPECTED.md` 的「取決於」欄有標示，主要是：

- `ALU_STATUS` 各旗標的位元位置（`c07`）
- 無號 SUB 的負結果如何延伸到 32 位元（`c03` 的最後一格）
- `PERI_RESULT_META` 的位元組排列（`c10`）

## 這套測試不涵蓋的

- **時間的合格標準**：第 3 層只提供量測與比對，不判定對錯（週期數本來就是待硬體提供的值）。
- **硬體事件**（`.vector`、`safe`、`BR.ERET`）：事件的來源由目標硬體定義，這裡不知道怎麼讓硬體產生事件，所以沒有測試。
- **影像時序的條件**（VBLANK／HBLANK、`*_COMMIT_ELIGIBLE`、`FRAME_END_EVT`）：需要時序產生器與相關 CSR，尚未納入。
- **兩邊搶共用資源**（CSR 仲裁器、Status Flag、I2C 匯流排）誰先誰後：第 3 層的 `t08` 只量「變慢多少」，不判定先後規則。
- **第 4 層沒有納入的 7 列**：見 `FAULTS.md` 最後一節。
- **移位方向無法做反向驗證**：其他編碼可以用「解碼端換一組編碼」確認測試抓得到，但移位方向寫死在工具裡，只能靠 `c06` 在硬體上實測。
- **取指方式**（EEPROM 或 SRAM）不影響這套測試的預期值：兩種方式下程式的行為相同，只有時間不同。
