# 積木式（拼圖式）編輯介面 — 分析與建議實作方式

目標：在 AssemblyCoreIDE 目前的**文字編輯**之外，提供第二種撰寫方式，仿 App Inventor 2（以下 AI2）：左邊選元件與積木、拼接成程式，
並能用屬性面板設定元件。本文件是設計分析，尚未實作；結尾列出需要你決定的事。

---

## 1. App Inventor 2 值得學的與不適用的

AI2 有兩個畫面：**Designer**（元件面板、檢視區、元件樹、屬性面板）與 **Blocks 編輯器**（Blockly）。

| AI2 的做法 | 對我們的價值 | 結論 |
|---|---|---|
| Designer：拖元件、在屬性面板改屬性 | 我們的「元件」是硬體：CSR、I2C 裝置、服務（service）、常數、DeviceMap、事件向量、Timer／Poll | **採用**，做成「硬體設計器」 |
| 每個元件自動產生專屬積木抽屜 | 一個 CSR 自動有「寫入／設位元／清位元／讀回」積木；裝置自動有「讀暫存器」積木 | **採用**（最大的易用性來源） |
| 事件積木（`when Button.Click`） | 對應 `.vector` 事件 handler、「收到服務 X」 | **採用** |
| 形狀與顏色表示型別（只有相容的才拼得上） | 這個 ISA 型別很少但限制很多（16 位元 ALU、scratchpad 位元組） | **採用**，用型別插槽防呆 |
| 積木上直接顯示錯誤／警告、計數 | 對應組譯器診斷與 W5xx 資料流警告 | **採用** |
| Typeblock（鍵盤輸入積木名稱就建立） | 熟手用鍵盤比拖曳快 | **採用** |
| 摺疊、停用、註解、背包、複製貼上、復原 | 一般編輯需求 | **採用** |
| 純積木、不能看文字 | 我們需要與 `.asm` 並存、可單步除錯 | **不採用**：保留文字並雙向 |
| 通用語言（變數、清單、字串、迴圈…） | ISA 沒有字串／清單／堆疊；只有 16 位元整數與位元組區域 | **只取需要的子集** |

## 2. 這個 ISA 對積木的特殊要求

1. **兩個 domain**：Main（有 MOV／ALU）與 Peri（只有 CSR／分支／PUB／XFER）→ 兩個工作區頁籤，共用元件定義。
2. **資料不在「變數」裡，在固定區域**：scratchpad 32 位元組、`ALU_OPA/OPB/OUT`、`MAIN_CSR_DATA_BUF`（唯讀 MOV 來源）、結果槽。積木要讓人用「值」思考，卻產生正確的位元組搬運。
3. **控制流只有條件分支**（8 位元目標、ConditionMap 固定條件）：「如果 a < b」要降階成 `MOV…→ALU`、`ALU CMP.LT`、`BR.COND ALU_CMP_TRUE`。
4. **容量有限**：每個 domain 程式 256 位元組、描述子表 32／64 項 → 積木介面要即時顯示用量。
5. **事件**：`safe` 分支與 handler 不保存狀態；人工很容易寫出 W512。積木的程式碼產生器可以**以構造保證**安全（見 §6.4）。
6. **所有規則已在 `asmcore` 裡**（診斷、WCET、資料流、模擬器）。積木層**不重做任何檢查**，只負責「編輯模型 → 組譯器文字」。

## 3. 技術選型：原生 Qt Widgets（建議）vs 內嵌 Google Blockly

| 面向 | A. 原生 Qt（`QGraphicsScene`） | B. Blockly（`QtWebEngine`） |
|---|---|---|
| 新增相依 | 無（目前 Qt kit 已有 Widgets） | **QtWebEngine**：目前 Windows MSVC kit 與 Linux Qt 都**沒有**（只有 Widgets／Test／Xml／OpenGL 等），要另外下載（Chromium，數百 MB），散佈檔增加約 150 MB 以上 |
| 與現有架構 | 完全符合：模型在 std C++17 服務層，UI 只畫 | 兩套語言（JS／C++）、需 `QWebChannel` 橋接；模型留在 JS 側或雙份 |
| 與組譯器／模擬器整合 | 同行程直接呼叫 | 全部要跨橋序列化（診斷、單步位置、WCET…） |
| 測試 | 模型可無視窗測；場景可 offscreen 測 | WebEngine 在 offscreen／CI 不穩 |
| 成熟度 | 要自己做拖放、吸附、縮放、復原…（工作量大但範圍小，見 §8） | 現成：吸附、抽屜、突變器、搜尋、本地化 |
| 外觀／彈性 | 完全客製（型別插槽、位元組格、資源計量） | 受 Blockly 主題限制，客製要寫 JS |
| 授權 | 自有 | Blockly Apache-2.0（與本專案相容） |
| 離線／部署 | 單一 exe | 要打包 JS 資源與 Chromium |

**建議 A（原生 Qt）**，理由：不引入大型相依、與服務層/組譯器同行程、可自動化測試、此語言的積木文法很小（語句堆疊＋值插槽，不需要 Blockly 的大部分通用功能）。

**保留退路**：把「積木定義」做成資料驅動的 JSON（類似 Blockly 的 block JSON：名稱、顏色、欄位、插槽型別、程式碼模板），模型層與渲染無關；
日後若決定改用 Blockly，只要換掉 `ui/` 的畫布，模型、定義、程式碼產生器、測試都能沿用。

## 4. 架構

```
 ui/blocks/        BlockCanvas（QGraphicsView）、Toolbox 抽屜、屬性面板、元件樹、資源計量、typeblock
   │
 services/blocks/  標準 C++17，無 Qt：
   │               BlockDef（積木定義註冊表）  BlockDocument（模型）  Connect（連接與型別規則）
   │               CodeGen（積木→.asm 文字＋來源對照）  Importer（.asm→積木）
   │               Edit commands（復原／重做）  Serialization（.acblk JSON）
   │               ComponentModel（CSR／裝置／服務／常數…）→ 產生 .inc 與環境檔
 ../core           asmcore：assemble / Index / SourceMap / lang 詞彙 / Simulator
```

### 4.1 積木定義從 `asmcore` 自動長出來

`core/include/asmcore/lang.h` 已有每個指令的簽名、運算元型別、domain、說明（懸停用）。`BlockDef` 註冊表**由這份詞彙表產生**
「一指令一積木」（Level 1），新增指令或 profile 的 ALU 碼變動時積木自動跟上；Level 2 的結構化積木另外手寫定義（資料驅動 JSON）。

### 4.2 模型（`BlockDocument`）

- 樹狀：`Program(domain)` → 有序的語句列（statement stack）；每個積木有欄位（dropdown／數字／文字）與值插槽（子積木）。
- 每個積木有穩定 `id`（UUID）；程式碼產生時寫入來源對照（積木 id ↔ 產生的行號範圍）。
- 型別：`u16`、`i16`、`byte`、`bool`（旗標，來自 ConditionMap 或 ALU 比較）、`bytes(n)`、`csr`、`service`、`label`、`device`。插槽宣告接受的型別；拖曳時只顯示可接的位置。

### 4.3 檔案與「單一事實來源」（最關鍵的決定）

雙向同步最容易出問題。建議**每個檔案有明確模式**，而不是即時雙向編輯：

| 檔案 | 事實來源 | 另一邊 |
|---|---|---|
| `foo.asm`（一般） | 文字 | 可用「以積木開啟」→ `Importer` 解析成積木（唯讀預覽或轉成積木檔） |
| `foo.acblk`（積木專案檔，JSON） | 積木 | 產生 `foo.generated.asm`（頭註解寫明「由積木產生，請勿手改」）；專案把它當一般來源組譯 |

- **無損逃生口**：`Raw asm` 積木可放任意一行／一段文字；`Importer` 遇到無法對應的語句（巨集、奇怪的 `.const`…）就產生 Raw 積木，**匯入永不失敗**。
- **保證往返**：Level 1 的 文字 → 積木 → 文字，組譯後的**映像位元組必須相同**（沿用我們已有的 round-trip 測試機制）。註解與空白以 Raw／註解積木保留。
- **分離（Detach）**：積木檔可「轉為文字」，之後只剩 `.asm`；反向用「以積木開啟」。
- 文字視圖：積木編輯器旁邊可開**唯讀的產生碼面板**，游標選積木 ↔ 反白對應文字行（靠來源對照），學習文字語法的好工具。

### 5.1 硬體設計器（AI2 的 Designer 對應）— 同時補上「環境檔表單模式」的缺口

元件 → 屬性（都有欄位驗證與即時預覽）：

| 元件 | 屬性 | 產生的內容 |
|---|---|---|
| CSR | 名稱、位址、每個位元的角色（`timer_start`／`poll_arm`…）、模擬種類（ram／value／action…） | `.csr`、`.csrbit`、環境檔 `[csr X]` |
| I2C 裝置 | 名稱、7 位元位址、DeviceMap 索引、暫存器表（位址→預設位元組） | `.devmap`、環境檔 `[device]` |
| 服務 | 名稱、id、payload 長度、位元組序（big／little）、發佈者（Peri 積木）／處理者（Main 積木） | `.service … , len=, big` |
| 常數 | 名稱、寬度、值 | `.const` |
| 事件 | id、domain、handler | `.vector` |
| 時序 | frame／vblank、Timer 週期 | 環境檔 `[timing]` |
| Profile | 以表單編輯 profile 鍵（SRAM 配置、對齊、ALU 碼…）與缺口清單 | `.profile` |

這與目前 IDE 計畫表 E1「環境檔表單模式 ⬜」重疊：**硬體設計器就是那個表單**，一次做兩件事。

## 6. 積木與程式碼產生

### 6.1 兩層積木

**Level 1 — 忠實層（一指令一積木）**：與文字 1:1，確保任何 `.asm` 都能顯示；也給熟手精確控制。
例：`MOV src → dst`（區域下拉＋位元組範圍選擇器，點擊 scratchpad 的 32 格位元組圖選範圍）、`ALU ADD [unsigned]`、`EXEC_CSR …`、`BR.COND 條件 → 標籤 [safe]`、`標籤:`、`CASCADE…`。

**Level 2 — 結構層（給初學者的高階積木）**，降階成 Level 1：

| 積木 | 降階 |
|---|---|
| 如果 條件 … 否則 … | `BR.COND` 到 then 標籤、else 內容、`JMP` 結尾（BR 只在條件成立時跳，所以反向用結構調整） |
| 當 條件 重複 … ／ 永遠重複 ／ 重複 N 次 | 迴圈標籤＋條件分支；「重複 N 次」自動配計數變數 |
| 等待直到 條件 | 自旋 `BR.COND` |
| 設 變數 ← 運算式、運算式 `+ − × & \| ^ << >> 比較` | 自動配置 scratchpad，產生 `MOV`／`ALU`／`MOV ALU_OUT` |
| 寫入 CSR／讀 CSR（元件積木） | `EXEC_CSR WRITE_SP`（先把值放進 scratchpad）／`READ8`＋`MOV` |
| 呼叫／程序（procedure） | `.proc`／`CALL`／`RET`（可選呼叫模型） |
| 收到服務 X（事件）／服務 X 的 payload 取值 | 自動產生「比對 service_id → 消耗 → 位元組序交換」整段樣板（見下） |
| 當事件 N 發生 | `.vector N, label`＋handler＋自動 `BR.ERET` |
| Peri：讀裝置暫存器 → 發佈服務 | `EXEC_XFER READ`＋`EXEC_PUB`；Poll／Timer 流程樣板（已啟動計時器、arm、READ RX[0]） |
| Cascade（選擇值＋N 個區塊插槽） | `CASCADE_BEGIN/END`，索引自動編號 |

### 6.2 變數與暫存器配置

- 使用者看到「變數」；產生器維護**配置器**：每個變數 16 位元（2 位元組）或 1 位元組，從 scratchpad 的**可用池**分配，避開 softret 保留區（`ret_slot_base`／`ret_stage_base`）與使用者標示的固定位元組（`.assume`）。
- **生命週期分析**（沿用 `dataflow` 的概念）讓短命暫存共用位元組；超出 32 位元組時給「scratchpad 用完」錯誤並指出哪些變數。
- 表達式求值順序固定：先把運算元 MOV 進 `ALU_OPA/OPB`、做 ALU、立刻 MOV 出 `ALU_OUT`，**不讓 ALU 狀態跨越任何分支**。

### 6.3 型別與線上位元組序

- 數值寬度為 16 位元；`取 payload 16 位元（高位元組先）` 積木自動插入交換序列，避免 W514。
- 比較結果是 `bool`，只能接在條件插槽；ConditionMap 的硬體條件（`PERI_RESULT_VALID`、`VBLANK_OPEN`…）是現成的 `bool` 積木。

### 6.4 事件與 `safe`：用構造保證，而不是猜

組譯器無法證明哪個分支「安全」（hardware 不保存 ALU／scratchpad）。積木產生器可以**由構造保證**：
- 前景的運算式都在一個語句內完成，不跨越檢查點；變數放進與 handler **不重疊**的 scratchpad 池（handler 的變數另配一池）。
- 於是每個迴圈的回邊可以自動加 `safe`（提供「此迴圈可被事件打斷」開關），並由 `analyzeEvents` 再驗證一次（W512 應為零；有就在該積木上顯示）。

### 6.5 與 ISA 限制的互動

- 8 位元分支目標：產生器把「熱迴圈」與短程分支放在前 256 位元組；超過時在積木上標示並建議拆程序。
- 描述子表與碼大小：工具列即時計量（讀 `Result` 的 `.map` 資訊）；快滿時變黃。
- WCET：每個 handler／程序顯示規劃週期（`wcet` 與 `eventTiming`）。

## 7. 診斷、除錯與其他整合

| 功能 | 做法 |
|---|---|
| 錯誤／警告 | 建置後把 `Diagnostic{file,line}` 經積木↔行號對照轉成積木 id，積木右上角顯示 ⚠／✖，懸停顯示原訊息與 `asmc --explain` 的修法；工作區角落顯示計數（同 AI2） |
| 除錯 | 現有 `Debugger`（行號中斷點、單步）不用改：積木上設中斷點 → 轉成產生碼的行；執行位置反向高亮積木。單步粒度可選「積木」或「指令」 |
| 狀態面板 | State／Memory／Signals 等沿用；scratchpad 面板可顯示「變數名稱」（配置器提供位元組→名稱對照） |
| 事件注入 | 與目前缺口（IDE 沒有即時注入對話框）一併補：積木工具列的「注入事件 N」 |
| 情境腳本 | 積木專案可附 `.scn`，IDE 補上「執行情境」按鈕（目前也是缺口） |
| 範例／教學 | 內建範本積木專案（點亮 CSR、IMU 讀取、事件計數…），對應 `sample/`；AI2 風格的互動教學可後做 |
| 多語系 | 積木文字、抽屜名稱、提示全走 `tr()`；與現有 zh_TW 流程一致 |

## 8. 畫布要自己做的東西（原生方案的工作清單）

吸附與連接（陰影預覽、可接位置高亮）、拖曳整串、抽屜（flyout）與搜尋、縮放／平移／小地圖、框選、剪貼簿（含跨專案）、復原／重做（`QUndoStack`）、
摺疊／停用（停用＝產生碼註解掉）、積木註解、背包、右鍵選單、鍵盤操作（Tab 在插槽間移動、Typeblock、Delete）、自動排列、匯出 PNG、高 DPI、無障礙名稱。
範圍雖多，但每項都小而獨立；積木文法簡單（單一語句堆疊＋值插槽，沒有突變器之外的複雜形狀）。

## 9. 測試策略

| 層 | 測試 |
|---|---|
| 模型 | 連接規則、型別檢查、序列化往返（JSON） |
| 程式碼產生 | **黃金輸出**：固定積木樹 → 預期 `.asm`；全部產出必須無 E 碼、零非預期警告 |
| 匯入 | `examples/`、`sample/`、反組譯輸出全部：文字 → 積木 → 文字 → **組譯後映像位元組相同** |
| 行為 | 結構化範例積木經產生器 → 模擬器跑情境腳本，與預期暫存器／CSR 值比對（同 `sample` 的 `.scn`） |
| 隨機 | 隨機合法積木樹 → 產生 → 組譯：不得有 E 碼；不變量：配置器不重疊、`safe` 不產生 W512 |
| UI | offscreen 以滑鼠事件模擬拖放、吸附、typeblock；快照比對關鍵形狀 |
| 整合 | 抽屜內容 = 詞彙表（新增指令時自動測到沒有積木的指令） |

## 10. 分階段計畫（每階段都可使用、可驗收）

| 階段 | 內容 | 驗收 |
|---|---|---|
| **B0 基礎** | `BlockDef`（由詞彙表產生）、`BlockDocument`、`.acblk` 序列化、Level 1 `CodeGen`、`Importer`（含 Raw 積木） | 所有範例/sample 文字→積木→文字映像相同；黃金測試 |

## 11. 風險與對策

| 風險 | 對策 |
|---|---|
| 文字與積木不同步、失去格式／註解 | 每檔單一事實來源＋Raw／註解積木＋往返測試（§4.3） |
| 結構層降階產生比手寫更大的程式（256 位元組很緊） | 資源計量＋Level 1 隨時可用＋產生器最佳化（共用描述子、短程分支排序）；提供 softret 選項 |
| 型別系統過度限制導致拼不起來 | 提供明確的轉換積木（零擴展、取低位元組…）而不是放寬規則 |
| 畫布工作量被低估 | 先做 B1 的最小可用（吸附、拖曳、typeblock），其餘逐項補；模型與畫布分離，畫布可重寫 |
| 日後想換 Blockly | 資料驅動的定義＋渲染無關的模型（§3 退路） |
| ISA 規格變動 | 積木由詞彙表與 profile 產生，與核心同步（沿用 `EXTENDING.md` 的原則） |
