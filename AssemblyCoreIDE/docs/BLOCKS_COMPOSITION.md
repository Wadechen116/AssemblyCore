# 積木的組合方式：上下（流程）與左右（運算元）

> 狀態：**定義草案，等使用者確認後實作**（建議插在 M2 與 M3 之間，稱 **M2b**，見最後一節）。
> 對應規格：`docs/ASM_SYNTAX.md`（運算元語法、資料流、讀寫權限）。

## 1. 為什麼現在只有上下組合

目前的 Level 1 積木是「**一指令一積木**」，運算元（`CONST(1, 1)`、`MAIN_SCRATCHPAD[0..0]`）只是積木裡的**文字欄位（晶片）**，
所以畫面上只看得到「一行接一行」的上下組合。

**這是我當初的取捨，不是限制**：模型與引擎其實已經支援左右組合（值插槽 `InputDef`、值積木 `valueType`、`plugValue`、型別檢查 H7、版面引擎
排插槽與插入的積木、`.acblk` 的 `values`），只是**沒有任何內建積木使用它**（只用測試用的自訂定義驗證過）。你說得對：組譯器語法裡
運算元本來就有結構（區域、範圍、常數、運算式），應該做成可左右組合的積木。下面是完整定義。

## 2. 兩個方向，各代表一件事

| 方向 | 組譯器語意 | 連接點 | 外形 |
|---|---|---|---|
| **上下**（流程） | 「執行完這條，接著執行下一條」——序列器的指令順序；`proc` 的 C 形槽＝程序本體 | 上凹／下凸（`Previous`／`Next`／`Slot`） | 方塊，上凹下凸 |
| **左右**（運算元） | 「這條指令的這個運算元**是**什麼」——一個值（區域、常數、數字運算式）插進指令的插槽 | 左側插頭 ↔ 右側插槽（`Plug`／`Socket`） | 圓角膠囊，**形狀依型別不同** |

指令與指令之間**只有上下**（序列器一步一條微指令，沒有「並排執行」這種語意）；左右只發生在「指令 ↔ 運算元」與「運算元 ↔ 運算元」。

## 3. 值的型別（由組譯器語法導出）

| 型別 | 意義 | 例 | 外形 |
|---|---|---|---|
| `int` | 數字運算式（位移、長度、指標、常數值） | `5`、`LIMIT`、`LIMIT + 1`、`1 << 3` | 圓形膠囊 |
| `region.r` | **可讀**的位元組區域（指令的來源） | `MAIN_SCRATCHPAD[0..1]`、`ALU_OUT`、`ALU_STATUS`、`MAIN_CSR_DATA_BUF[0..1]`、`PERI_RESULT_SLOT[..]`、`MAIN_CONST_POOL[@name]`、`CONST(5, 2)` | 左右帶圓角的膠囊 |
| `region.w` | **可寫**的位元組區域（指令的目的） | `MAIN_SCRATCHPAD[0..1]`、`ALU_OPA`、`ALU_OPB`、`PERI_…` | 同上，右緣加標記 |
| `region.rw` | 可讀可寫（`MAIN_SCRATCHPAD[..]`） | | 同上，兩側標記 |
| `label` | 程式位置（標籤／程序名） | `start`、`handle` | 下拉（保持欄位，不做積木） |

可讀／可寫的對照直接取自 `ASM_SYNTAX.md` 的區域表（`ALU_OPA/OPB` 只能寫、`ALU_OUT/STATUS` 只能讀、`MAIN_SCRATCHPAD` 都可以……），
**不另立規則**——表由程式從同一份資料產生，改規格就改表。

## 4. 值積木（插頭在左，可以插進插槽）

**區域類**（型別 `region.*`）
| 積木 | 內容（左右可再插 `int`） | 產生 |
|---|---|---|
| 暫存區 | `scratchpad [first] .. [last]` | `MAIN_SCRATCHPAD[first..last]` |
| ALU 輸入 A／B | `ALU A`、`ALU B`（無插槽；固定 offset 0、長度 2） | `ALU_OPA`／`ALU_OPB` |
| ALU 結果／狀態 | `ALU out`、`ALU status` | `ALU_OUT`／`ALU_STATUS` |
| CSR 緩衝 | `CSR buffer [first] .. [last]` | `MAIN_CSR_DATA_BUF[..]` |
| 結果槽（Peri） | `result slot [first] .. [last]` | `PERI_RESULT_SLOT[..]` |
| 常數池項目 | `const pool [@name]` | `MAIN_CONST_POOL[@name]` |
| 常數 | `constant [value] bytes [n]` | `CONST(value, n)` |

**數字類**（型別 `int`）
| 積木 | 內容 | 產生 |
|---|---|---|
| 數字 | 欄位直接輸入 | `5`、`0x20` |
| 名稱 | 下拉：目前檔案／硬體描述定義的 `.equ`／`.const`／CSR 名 | `LIMIT` |
| 運算 | `[a] + [b]`（`+ - * / & | ^ << >>`，各是 `int`） | `(a + b)` |
| 括號 | 包住一個運算式 | `(a)` |

**規則**：空的 `int` 插槽直接顯示**行內數字欄位**（和現在一樣打字即可）——只有要做「運算式」時才插運算積木。
所以 `MAIN_SCRATCHPAD[0..1]` 的 `0`、`1` 平常是數字欄位，不會變成一堆小積木。

## 5. 指令積木的插槽（Level 1 全部改成「插槽版」）

| 指令積木 | 插槽（左右） | 型別要求 |
|---|---|---|
| `mov` 搬移 | `from [ ]` `to [ ]` | from：`region.r`；to：`region.w` |
| `alu` | 運算為下拉；無運算元插槽（ALU 只吃 ALU_OPA／OPB） | — |
| `csr_write8/set8/clr8` | `csr [名稱或 int]` `value [int]` | `int` |
| `csr_write_sp` | `csr`、`len [int]`、`ptr [int]` | `int` |
| `csr_read8/read_buf` | `csr`、`len` | `int`；目的固定為 CSR 緩衝 |
| `br_cond`／`jmp`／`call` | 條件與目標為下拉（`label`） | — |
| `xfer`／`pub`（Peri） | 依其運算元：`int`／`region` | 依表 |

## 6. 「能不能接」——逐對的 Assembly 語意規則

吸附只有在**兩兩符合**時成立（你的 D1）；不符的顯示**斜紋**並說明原因。新增的左右規則（加入現有 H/S 規則）：

| 規則 | 等級 | 內容 |
|---|---|---|
| **H7a** 型別 | 硬 | `int` 只能插 `int` 插槽；`region.r` 只能插「來源」插槽；`region.w` 只能插「目的」插槽；`region.rw` 兩邊都可 |
| **H7b** 讀寫權限 | 硬 | 例：`ALU out` 不能當 `mov.to`（唯讀）；`ALU A` 不能當 `mov.from`（唯寫）；`CSR buffer` 在 `mov` 只能當來源（v31 `csrbuf` MOV 唯讀） |
| **H7c** 常數池 | 硬 | `const pool …` 與 `constant …` 當來源時，**目的必須是暫存區**（不可直接進 ALU、也不可進 CSR 緩衝）——這是**兩個插槽之間**的規則，插第二個時檢查 |
| **H7d** 範圍 | 硬／軟 | 兩端都是數字時檢查 `first ≤ last`、不超出區域大小（暫存區 32 位元組等，值取自 Profile）；含名稱／運算式的只在組譯時檢查（軟：顯示警告） |
| **H7e** 域 | 硬 | `result slot`／Peri 專用區域只能放在 Peri 堆疊的指令；Main 專用區域放進 Peri 指令即不符（沿用 H1 的做法） |
| **H7f** 唯一 | 硬 | 一個插槽只有一個積木；插入已佔用的插槽 → 原來的彈出成漂浮積木（或拒絕，見問題 3） |

**不完整的指令**（必填插槽是空的）：積木顯示錯誤徽章「`to` 還沒有運算元」；產生文字時該行輸出成註解
`; (incomplete) MOV … -> ?`，讓組譯器不會吃到半截指令，也不會默默漏掉。

## 7. 與文字互轉（單一真實來源不變）

- **產生**：值積木各有一小段範本，指令範本用 `{from}`、`{to}`；結果仍是**一行**，所以 `assemble(generate(import(t)))` 位元組不變（沿用 B0 的保證與測試）。
- **匯入**：運算元用一個小型 parser 拆成值積木（`MAIN_SCRATCHPAD[0..1]` → 暫存區＋兩個數字欄位；`CONST(5,2)` → 常數；
  `LIMIT + 1` → 運算）。**拆不開的運算元不失敗**：變成一個「原文」值積木（型別 `any`，保留原字串，用等寬字顯示），和 `raw` 同一個精神。
- **舊檔相容**：現有 `.acblk`（欄位文字版）開啟時自動升級成插槽版，存檔後才是新格式；欄位文字保持相同。

## 8. 畫面與操作（M3 接手）

- 插頭／插槽的形狀依型別不同，**形狀不合根本放不進去**（先看形狀，再看斜紋）。
- 拖曳值積木靠近插槽時：能接→插槽亮起；不能接→斜紋＋原因；放開在空白處→變漂浮積木（可以先擺著再組）。
- 插槽裡的積木拖出來就脫離（變漂浮），拖回去又接上；整排展開太寬時換行（版面引擎已支援行高自適應）。

## 10. 需要你確認的問題

1. **「左右組合」＝指令與運算元之間**（上面第 2、5 節），指令與指令之間仍只有上下——是這個意思嗎？
2. 數字的行內欄位（平常 `0`、`1` 不變成小積木，要運算才插運算積木）——OK 嗎？還是**每個數字都要是獨立積木**？
3. 插入已佔用的插槽時：**原積木彈出成漂浮**（建議，不會丟資料）還是拒絕？
4. 現有檔升級成插槽版後，舊版 IDE 就不能開了——可以接受嗎？
5. 先做 M2b 再做 M3（建議；這樣拖曳吸附一次處理上下與左右），還是先做 M3 的上下拖曳、M2b 之後補？
